# Интеграция с 1С

Backend предоставляет отдельный JSON/HTTP-контур для обмена с 1С. Он не зависит от внутренней структуры конкретной конфигурации 1С и может вызываться из HTTP-сервиса, обработки или другого интеграционного модуля на стороне 1С.

## Безопасность

Интеграция использует отдельный ключ, а не JWT учетной записи сотрудника.

В окружении backend необходимо задать:

```text
CEH_INTEGRATION_API_KEY=<длинный случайный ключ>
```

Каждый запрос 1С должен передавать заголовок:

```text
X-Integration-Key: <тот же ключ>
```

Если ключ в backend не настроен, интеграционные маршруты отвечают `503`. Неверный ключ получает `401`.

Для production обмен должен идти только по HTTPS. Ключ интеграции не следует хранить в мобильном или веб-клиенте.

## Получение данных из «Цех — склад»

### Полный текущий снимок

```text
GET /api/v1/integration/1c/snapshot
```

Ответ содержит:

- склады;
- товары с розничной и оптовой ценой;
- торговых представителей;
- текущие остатки по складам;
- текущие остатки у представителей;
- текущую задолженность каждого представителя;
- время формирования снимка.

Полный снимок удобно использовать при первоначальном подключении, контрольной сверке или восстановлении интеграции. Для регулярного обмена больших журналов следует использовать курсорные маршруты ниже.

### Последние товарные документы

```text
GET /api/v1/integration/1c/documents?limit=200
```

Возвращается журнал документов вместе со строками товара, статусом и суммой продажи. Сторнированные документы остаются в журнале со статусом `cancelled`.

### Инкрементальные изменения товарных документов

Первый запрос выполняется без курсора:

```text
GET /api/v1/integration/1c/documents/changes?limit=200
```

Ответ имеет вид:

```json
{
  "items": [],
  "next_cursor": "непрозрачный-курсор",
  "has_more": false
}
```

Если `has_more=true`, 1С должна запросить следующую страницу:

```text
GET /api/v1/integration/1c/documents/changes?limit=200&cursor=<next_cursor>
```

Курсор привязан к времени последнего изменения документа и его идентификатору. Поэтому уже выгруженный документ повторно появится в потоке, если позже его сторнируют и статус изменится с `posted` на `cancelled`.

### Последние денежные проводки

```text
GET /api/v1/integration/1c/money-postings?limit=200
```

Возвращаются продажи, сдачи денег и компенсирующие корректировки. Записи не удаляются.

### Инкрементальные денежные проводки

Первый запрос:

```text
GET /api/v1/integration/1c/money-postings/changes?limit=200
```

Следующие страницы:

```text
GET /api/v1/integration/1c/money-postings/changes?limit=200&cursor=<next_cursor>
```

Структура ответа такая же: `items`, `next_cursor`, `has_more`. Денежные проводки неизменяемы, поэтому курсор строится по времени создания и идентификатору записи.

### Правило сохранения курсора

`next_cursor` является непрозрачной строкой. 1С не должна разбирать или самостоятельно формировать его.

Рекомендуемый алгоритм:

1. Получить страницу с текущим сохраненным курсором или без него при первом запуске.
2. Идемпотентно обработать все элементы `items`.
3. Только после успешной фиксации всей страницы сохранить `next_cursor` в 1С.
4. Если `has_more=true`, сразу запросить следующую страницу.
5. При сетевом сбое повторить запрос со старым сохраненным курсором.

Такой порядок не теряет данные при падении между получением ответа и записью результатов в 1С. Повторно полученные элементы должны обрабатываться идемпотентно по `id`.

Поврежденный или некорректный курсор получает ответ `422`. В этом случае интеграционный модуль должен зафиксировать ошибку и либо восстановить последний корректный курсор из своего хранилища, либо выполнить контрольную полную синхронизацию.

## Передача операций из 1С

Доступны маршруты:

```text
POST /api/v1/integration/1c/operations/receipt
POST /api/v1/integration/1c/operations/issue-to-representative
POST /api/v1/integration/1c/operations/warehouse-transfer
POST /api/v1/integration/1c/operations/representative-return
POST /api/v1/integration/1c/operations/sale
POST /api/v1/integration/1c/operations/payment
```

Формат тела совпадает с основными операционными DTO backend. Для всех операций 1С поле `external_id` обязательно.

Рекомендуемый формат идентификатора:

```text
1c:<тип_объекта>:<уникальный_идентификатор_1с>
```

Например:

```text
1c:document-sale:8f4a5e1c-3b7a-4e34-9d12-13f0d49b5031
```

Если 1С повторно отправит операцию с тем же `external_id` после сетевого сбоя, backend вернет уже созданный результат и не проведет движение второй раз.

После успешного импорта backend рассылает обычное WebSocket-событие `state_changed`, поэтому Android-клиенты получают новые остатки и задолженность тем же механизмом, что и при операциях из веб-панели.

## Ответственность систем

Рекомендуемая схема внедрения:

1. Определить, какая система является владельцем справочника товаров и цен.
2. Зафиксировать соответствие UUID backend и ссылок/уникальных идентификаторов 1С.
3. Включить обязательный `external_id` для всех документов обмена.
4. Сначала запустить обмен в тестовой базе на копии реальных данных.
5. Сверить остатки, задолженность и обороты за контрольный период.
6. После сверки включить курсорную выгрузку журналов.
7. Только затем включать полностью автоматическую двустороннюю синхронизацию.

Не рекомендуется давать 1С прямой доступ к таблицам PostgreSQL: интеграционный API сохраняет проверки отрицательных остатков, блокировки, идемпотентность и единый журнал проводок.
