# Интеграция с 1С

Backend предоставляет отдельный JSON/HTTP-контур для обмена с 1С. Он не зависит от внутренней структуры конкретной конфигурации 1С и может вызываться из HTTP-сервиса, обработки или другого интеграционного модуля на стороне 1С.

## Безопасность

Интеграция использует отдельный ключ, а не JWT учетной записи сотрудника.

В окружении backend необходимо задать:

```text
CEH_INTEGRATION_API_KEY=<длинный случайный ключ>
```

Каждый запрос 1С должен передавать заголовок:

```text
X-Integration-Key: <тот же ключ>
```

Если ключ в backend не настроен, интеграционные маршруты отвечают `503`. Неверный ключ получает `401`. Для production обмен должен идти только по HTTPS; ключ интеграции нельзя хранить в мобильном или веб-клиенте.

## Полный текущий снимок

```text
GET /api/v1/integration/1c/snapshot
```

Ответ содержит склады, товары с двумя ценами, торговых представителей, текущие остатки, задолженность, время формирования снимка и постоянные соответствия справочников в `entity_links`.

Полный снимок нужен при первоначальном подключении, контрольной сверке или восстановлении интеграции. Для регулярного обмена журналами следует использовать курсорные маршруты.

## Постоянные соответствия справочников

Backend хранит устойчивую связь между UUID внутренней сущности и ссылкой/уникальным идентификатором объекта 1С. Поддерживаются типы:

- `warehouse` — склад;
- `product` — товар;
- `representative` — торговый представитель.

### Создать или изменить соответствие

```text
PUT /api/v1/integration/1c/entity-links
```

Пример:

```json
{
  "entity_type": "product",
  "backend_id": "2dbf93e0-2c9c-4f07-b68d-c1ef1ca0aa42",
  "external_ref": "8f4a5e1c-3b7a-4e34-9d12-13f0d49b5031"
}
```

Для одной сущности backend может существовать только одна ссылка 1С соответствующего типа. Одна и та же ссылка 1С также не может быть назначена двум сущностям одного типа. Повторный `PUT` для того же `backend_id` заменяет его старую ссылку.

Backend проверяет, что целевой склад, товар или представитель действительно существует. Несуществующий UUID получает `404`, конфликт уже занятой ссылки — `409`.

### Получить весь реестр

```text
GET /api/v1/integration/1c/entity-links
```

Каждая запись дополнительно содержит `backend_code` и `backend_name`, чтобы интеграционный модуль мог диагностировать привязку без прямого доступа к БД.

### Найти UUID backend по ссылке 1С

```text
GET /api/v1/integration/1c/entity-links/resolve?entity_type=product&external_ref=<ссылка-1С>
```

Если соответствие существует, ответ содержит `backend_id`, код/артикул и имя объекта. Если соответствие отсутствует — `404`.

### Рекомендуемое первоначальное сопоставление

1. Получить `/snapshot`.
2. Один раз сопоставить объекты по проверяемым бизнес-признакам: коду склада, артикулу товара, коду представителя.
3. Зафиксировать каждую пару через `PUT /entity-links`.
4. После этого использовать ссылку 1С как устойчивый внешний идентификатор и при необходимости получать UUID backend через `/entity-links/resolve`.
5. Не выполнять автоматическое сопоставление только по наименованию: одинаковые или переименованные объекты могут дать ложную связь.

## Товарные документы

Последние документы:

```text
GET /api/v1/integration/1c/documents?limit=200
```

Возвращается журнал документов вместе со строками товара, статусом, аудитом и суммой продажи. Сторнированные документы остаются в журнале со статусом `cancelled`.

### Инкрементальные изменения

Первый запрос:

```text
GET /api/v1/integration/1c/documents/changes?limit=200
```

Ответ:

```json
{
  "items": [],
  "next_cursor": "непрозрачный-курсор",
  "has_more": false
}
```

Следующая страница:

```text
GET /api/v1/integration/1c/documents/changes?limit=200&cursor=<next_cursor>
```

Курсор строится по времени последнего изменения документа и UUID. Поэтому уже выгруженный документ повторно появится в потоке, если позднее его сторнируют и статус изменится с `posted` на `cancelled`.

## Денежные проводки

Последние проводки:

```text
GET /api/v1/integration/1c/money-postings?limit=200
```

Инкрементально:

```text
GET /api/v1/integration/1c/money-postings/changes?limit=200
GET /api/v1/integration/1c/money-postings/changes?limit=200&cursor=<next_cursor>
```

Структура страницы та же: `items`, `next_cursor`, `has_more`. Денежные проводки неизменяемы, поэтому курсор строится по времени создания и UUID записи.

## Правило сохранения курсора

`next_cursor` — непрозрачная строка. 1С не должна разбирать или самостоятельно формировать его.

Рекомендуемый алгоритм:

1. Получить страницу с текущим сохраненным курсором или без него при первом запуске.
2. Идемпотентно обработать все элементы `items`.
3. Только после успешной фиксации всей страницы сохранить `next_cursor` в 1С.
4. Если `has_more=true`, сразу запросить следующую страницу.
5. При сетевом сбое повторить запрос со старым сохраненным курсором.

Повторно полученные элементы должны обрабатываться идемпотентно по `id`. Поврежденный курсор получает `422`; в этом случае следует восстановить последний корректный курсор либо выполнить контрольную полную синхронизацию.

## Передача операций из 1С

Доступны маршруты:

```text
POST /api/v1/integration/1c/operations/receipt
POST /api/v1/integration/1c/operations/issue-to-representative
POST /api/v1/integration/1c/operations/warehouse-transfer
POST /api/v1/integration/1c/operations/representative-return
POST /api/v1/integration/1c/operations/sale
POST /api/v1/integration/1c/operations/payment
```

Формат тела совпадает с основными операционными DTO backend. Для всех операций 1С поле `external_id` обязательно.

Рекомендуемый формат:

```text
1c:<тип_объекта>:<уникальный_идентификатор_1с>
```

Например:

```text
1c:document-sale:8f4a5e1c-3b7a-4e34-9d12-13f0d49b5031
```

Если 1С повторно отправит операцию с тем же `external_id` после сетевого сбоя, backend вернет уже созданный результат и не проведет движение второй раз.

После успешного импорта backend рассылает стандартное WebSocket-событие `state_changed`, поэтому Android и веб-панель получают новые остатки и задолженность тем же механизмом, что и при пользовательских операциях.

## Ответственность систем

Перед production-включением обмена рекомендуется:

1. Определить владельца справочника товаров и цен.
2. Выполнить и проверить первичное сопоставление справочников через `entity-links`.
3. Использовать обязательный `external_id` для документов обмена.
4. Проверить обмен на копии реальных данных.
5. Сверить остатки, задолженность и обороты за контрольный период.
6. Включить курсорную выгрузку журналов.
7. Только после сверки включать полностью автоматическую двустороннюю синхронизацию.

Не рекомендуется давать 1С прямой доступ к PostgreSQL: интеграционный API сохраняет проверки отрицательных остатков, блокировки, аудит, идемпотентность и единый журнал проводок.
