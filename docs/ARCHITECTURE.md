# Архитектура системы

## Контуры

1. **Backend** — единственный источник истины по остаткам и задолженности представителей.
2. **Android** — рабочее место торгового представителя: просмотр складов и цен, собственный остаток, продажи, возвраты и сдача денег.
3. **Admin Web** — управление номенклатурой, складами, пользователями, перемещениями и отчетностью.
4. **1С** — внешний учетный контур. Интеграция выполняется через стабильные внешние идентификаторы и версионированный API.

## Модель остатков

Каждый физический склад и каждый торговый представитель представлены как `Location`. У представителя это виртуальный склад. Поэтому выдача товара представителю технически является обычным перемещением между двумя местами хранения.

Текущий остаток хранится в `inventory_balances`, а история — в `stock_documents`, `stock_document_lines` и `stock_movements`.

Запрещается прямое изменение остатка через пользовательский API. Любая операция должна создать документ и движения.

## Защита от гонок

При списании сервер блокирует строку остатка `SELECT ... FOR UPDATE`, проверяет доступное количество и только после этого формирует проводки. Это предотвращает двойное списание при одновременной работе нескольких устройств.

## Денежный учет

`money_transactions` — отдельный регистр задолженности торгового представителя:

- продажа — положительная сумма, увеличивающая долг;
- сдача денег — отрицательная сумма, уменьшающая долг;
- корректировка — служебная операция администратора с обязательным комментарием.

## Роли

- `representative` — только собственные операции и доступные остатки/цены;
- `admin` — справочники, пользователи, проведение и исправление операций;
- `manager` — чтение всех данных, отчеты, контроль задолженности и движений.

Проверка прав будет реализована на уровне серверного API; скрытие кнопки в интерфейсе не считается защитой.

## Real-time

После проведения движения backend отправляет событие `stock_changed` по WebSocket. Клиенты при получении события повторно запрашивают актуальный срез остатков через REST API.
