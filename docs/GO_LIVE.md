# Go-live: переход к реальной эксплуатации

Этот документ задаёт порядок допуска после завершения технического hardening. Переход к следующему этапу выполняется только после прохождения предыдущего; секреты, пароли, приватные ключи и пользовательские данные в отчёты и Git не записываются.

Связанные документы: `docs/GITHUB_RULESET.md`, `docs/PRODUCTION.md`, `docs/BACKUP.md`, `docs/ANDROID_RELEASE.md`, `docs/ANDROID_RELEASE_ARTIFACT.md`, `docs/ANDROID_SMOKE.md`, `docs/INTEGRATION_1C.md`, `docs/INTEGRATION_UNF_CLOUD.md`, `docs/RELEASE_CHECKLIST.md`.

## Gate 0. Защита исходного кода

Перед первым production deployment:

1. В GitHub должен быть активен ruleset `Защита main` из `.github/rulesets/main.json`.
2. Изменения в `main` должны идти через pull request.
3. Обязательные status checks:
   - `Итоговая проверка проекта`;
   - `Проверить production и Android release-контракты`.
4. Force-push и удаление `main` должны быть запрещены.
5. Автоматическое обновление lock-файлов должно создавать PR, а не писать напрямую в `main`.

Для применения ruleset используйте инструкцию `docs/GITHUB_RULESET.md` и workflow `Применить защиту main`. После применения обязательно перепроверьте GitHub **Settings → Rules → Rulesets**.

**Gate пройден**, когда ruleset имеет состояние Active и оба обязательных check видны в настройках защиты ветки.

## Этап 1. Реальный сервер и домен

### DNS и сеть

- выбрать рабочий DNS-домен;
- направить A/AAAA на production host;
- открыть наружу только 80/443, если инфраструктура не требует иного;
- PostgreSQL 5432 и backend 8000 не публиковать напрямую в интернет;
- проверить корректное время/NTP на хосте.

### Production env

На сервере, а не в Git:

```bash
python scripts/prepare_production_env.py \
  --domain <REAL_DOMAIN> \
  --email <REAL_ACME_EMAIL>
```

Сохранить временный bootstrap password и постоянные секреты в менеджере секретов. Не передавать содержимое `.env.production` в issue, PR, чат или логи. Bootstrap-пара используется только для создания первого администратора.

### Read-only preflight

```bash
python scripts/deploy_production.py --check-only
```

Ошибки DNS, прав файла, Docker daemon/Compose или production Compose должны быть устранены до запуска.

### Deployment

```bash
python scripts/deploy_production.py
```

После старта проверить минимум:

```bash
curl --fail https://<REAL_DOMAIN>/health
curl --fail https://<REAL_DOMAIN>/health/ready
```

Также проверить web-панель, TLS-сертификат, CORS/Origin и прикладной WebSocket через реальный HTTPS origin.

### Закрыть bootstrap после первичной инициализации

1. Войти bootstrap-администратором.
2. Немедленно сменить временный пароль.
3. Выйти и подтвердить повторный вход уже новым паролем.
4. Удалить из `.env.production` обе строки `BOOTSTRAP_ADMIN_LOGIN` и `BOOTSTRAP_ADMIN_PASSWORD`.
5. Повторно применить Compose без rebuild:

```bash
python scripts/deploy_production.py --skip-backup --no-build
```

6. Ещё раз проверить `/health/ready` и вход новым паролем.

Существующий администратор хранится в PostgreSQL; удаление bootstrap-пары не удаляет пользователя. Не отключайте bootstrap до подтверждённого повторного входа новым паролем.

**Этап 1 пройден**, когда HTTPS/readiness зелёные, наружу доступны только ожидаемые порты, постоянный пароль администратора проверен, а временные `BOOTSTRAP_ADMIN_*` отсутствуют в production env.

## Этап 2. Production backup и monitoring

До загрузки реальных хозяйственных данных:

1. Выполнить первую production-копию:

```bash
./scripts/backup.sh --production
```

2. Убедиться, что созданы dump, SHA-256 и metadata и что dump проходит встроенную проверку `pg_restore --list`.
3. Настроить отдельное off-site место — другой сервер/volume/object storage через поддерживаемый `rclone` remote.
4. Выполнить ручную off-site отправку и убедиться, что dump, checksum и metadata реально появились на удалённой стороне.
5. Установить и включить подготовленный systemd timer ежедневного backup/off-site.
6. Установить и включить production-monitor timer.
7. Если используется alert webhook — отправить тестовое уведомление и убедиться, что оно получено.
8. Провести тест восстановления в отдельную БД/контур; не проверять restore поверх рабочей БД.

**Gate пройден**, когда последняя локальная и off-site копии валидны, checksum совпадает, restore drill успешен, мониторинг и таймеры активны.

## Этап 3. Подписанный Android 0.4.0

Android 0.4.0 собирается с `compileSdk=36`, `targetSdk=36` и зафиксированным Gradle Wrapper.

В GitHub Secrets должны быть настроены, без публикации значений:

- `CEH_ANDROID_KEYSTORE_BASE64`;
- `CEH_ANDROID_KEYSTORE_PASSWORD`;
- `CEH_ANDROID_KEY_ALIAS`;
- `CEH_ANDROID_KEY_PASSWORD`.

Запустить workflow **`Подписанный Android release`** с параметром:

```text
api_base_url=https://<REAL_DOMAIN>/
```

Workflow должен использовать актуальный `main` с зелёным CI, собрать APK/AAB, проверить подпись и сформировать release manifest и `SHA256SUMS.txt`.

Перед установкой проверить:

- `versionName = 0.4.0`;
- application id `ru.ceh.sklad`;
- API base URL — именно production HTTPS origin;
- source commit совпадает с коммитом релиза;
- SHA-256 APK совпадает с release manifest/SHA256SUMS;
- signer certificate SHA-256 соответствует сохранённому production signing certificate.

**Gate пройден**, когда GitHub Release содержит проверенные подписанные APK/AAB и manifest/checksum для одного конкретного production commit.

## Этап 4. Physical-device UAT

UAT выполняется именно подписанным production APK на физическом Android-устройстве. В отчёт записывать только модель устройства, Android version/API, app version, APK SHA-256, дату, тестовый аккаунт/роль без пароля и результат сценария.

Минимальные сценарии:

1. Первый вход торгового представителя по мобильной сети и Wi-Fi.
2. Просмотр остатков нескольких складов и обеих цен.
3. Администратор выдаёт товар представителю; новое состояние появляется на устройстве.
4. Онлайн-продажа уменьшает остаток представителя и увеличивает долг.
5. Сдача денег уменьшает долг и появляется в истории.
6. Возврат товара представителем на склад корректно меняет оба остатка.
7. Офлайн-продажа сохраняется в очереди без ложного подтверждения проведения.
8. После восстановления сети операция отправляется один раз с тем же operation key; повторной продажи нет.
9. Конфликт/ошибка офлайн-операции виден пользователю и не теряется автоматически.
10. Выход из одного аккаунта и вход другого не показывает и не отправляет чужую офлайн-очередь.
11. Real-time обновление работает через production `wss://` без токена в URL.
12. Смена пароля инвалидирует старую сессию.
13. Удаление приложения/переустановка не восстанавливает старую авторизацию из Android Backup.
14. После нескольких операций сверить журнал документов, денежный журнал и отчёт руководителя с ожидаемыми значениями.

**Gate пройден**, когда все критичные сценарии пройдены без потери/дублирования данных. Любой дефект в продаже, остатках, долге, offline queue или идентичности пользователя блокирует go-live.

## Этап 5. Реальная облачная 1С:УНФ

Подключение выполняется только после успешного physical-device UAT.

До записи данных определить и зафиксировать вне секретов:

- точный production tenant/URL облачной УНФ;
- версию/вариант УНФ и доступные HTTP/OData/extension interfaces;
- тестовую организацию/склады для первой сверки, если возможно;
- правила соответствия UUID `ceh-sklad` ↔ GUID/ссылкам УНФ;
- кто является master-системой для товаров, цен, складов, продаж, оплат и возвратов.

Использовать отдельный `INTEGRATION_1C_API_KEY`, не JWT пользователя.

Последовательность:

1. Выполнить tenant audit/probe по `docs/INTEGRATION_UNF_CLOUD.md` без массовой записи.
2. Проверить metadata/доступные сущности и права интеграционной учётной записи.
3. Импортировать/сопоставить небольшой контролируемый набор товаров и складов.
4. Проверить отсутствие дублей external id/GUID.
5. Выполнить одну контролируемую операцию обмена и сверить её по обеим системам.
6. Проверить повтор того же `external_id`/operation key — повторная хозяйственная операция не должна возникнуть.
7. Проверить incremental cursors и восстановление обмена после остановки.
8. Отдельно сверить продажи, возвраты и денежные операции.
9. Сохранить результаты сверки: идентификаторы объектов, суммы, количества и временные метки без паролей/ключей.
10. Только после успешной сверки включать регулярный production sync.

**Gate пройден**, когда контрольные остатки, документы и деньги согласованы между `ceh-sklad` и УНФ и повторная доставка не создаёт дублей.

## Go / No-Go

Production запуск разрешён только если одновременно выполнено всё ниже:

- GitHub ruleset для `main` реально Active;
- оба обязательных CI checks зелёные на release commit;
- production HTTPS `/health` и `/health/ready` зелёные;
- постоянный пароль администратора проверен, временные `BOOTSTRAP_ADMIN_*` удалены из production env;
- локальный и off-site backup проверены, restore drill пройден;
- production monitoring/timers активны;
- подписанный Android 0.4.0 соответствует production домену, commit, checksum и signer certificate;
- physical-device UAT пройден;
- реальная УНФ прошла контролируемую двустороннюю сверку;
- нет открытого критичного дефекта, способного изменить остатки, задолженность, деньги или создать дубли документов.

Если хотя бы один пункт не выполнен — решение **No-Go**.

## Rollback

При критичной проблеме после начала эксплуатации:

1. остановить регулярный обмен с УНФ, чтобы не распространять ошибочное состояние;
2. зафиксировать affected operation keys, document ids, integration cursors и точное время инцидента;
3. не удалять и не переиспользовать idempotency/external ids;
4. сделать дополнительную backup-копию текущего состояния перед исправлениями, если БД доступна и консистентна;
5. откатить приложение/контейнеры на заведомо проверенный commit только по утверждённой процедуре;
6. restore БД выполнять лишь в отдельном окне обслуживания и только если логическая компенсация/исправление невозможны;
7. после восстановления снова проверить Alembic revision, `/health/ready`, контрольные остатки/долги и cursors интеграции;
8. возобновлять УНФ sync только после повторной сверки.

Нельзя «лечить» production прямым редактированием таблиц без зафиксированной процедуры и сверки регистров.
