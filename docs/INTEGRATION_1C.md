# Интеграция с 1С

## Общий принцип

Обмен двусторонний, идемпотентный и журналируемый. 1С работает только через отдельный сервисный ключ `X-1C-Key`; пользовательские JWT для обмена не используются.

## Настройка

В окружении backend задается отдельный секрет:

```env
INTEGRATION_1C_API_KEY=длинный-случайный-ключ
```

Все запросы 1С передают заголовок:

```http
X-1C-Key: длинный-случайный-ключ
```

Базовый адрес методов: `/api/v1/integration/1c`.

## Импорт справочников

### Номенклатура

`POST /products`

```json
{
  "operation_key": "product-42-version-7",
  "external_1c_id": "42",
  "sku": "A-001",
  "name": "Продукция А",
  "unit_name": "кг",
  "retail_price": "350.00",
  "wholesale_price": "310.00",
  "is_active": true
}
```

Если `external_1c_id` уже существует, справочник обновляется. Повтор запроса с тем же `operation_key` и тем же содержимым возвращает прежний результат и не создает дубль. Использование того же ключа с другим содержимым возвращает HTTP 409.

### Склады и виртуальные склады представителей

`POST /locations`

```json
{
  "operation_key": "location-main-version-2",
  "external_1c_id": "warehouse-main",
  "name": "Основной склад",
  "kind": "warehouse"
}
```

Для виртуального склада торгового представителя `kind` равен `representative`.

## Импорт остатков / инвентаризации

`POST /stock-adjustments`

```json
{
  "operation_key": "inventory-2026-09-03-main",
  "external_1c_id": "inventory-doc-10015",
  "location_external_1c_id": "warehouse-main",
  "comment": "Инвентаризация из 1С",
  "items": [
    {
      "product_external_1c_id": "42",
      "quantity_delta": "15.500"
    }
  ]
}
```

Это именно корректировка на дельту, а не прямое редактирование регистра. Документ и движения сохраняются в общей истории. Внешний идентификатор документа уникален, поэтому повторный импорт не создаст второе движение даже при использовании другого `operation_key`.

## Выгрузка из ceh-sklad в 1С

`GET /outbox?limit=50` возвращает неподтвержденные документы:

- перемещения склад → склад;
- выдачи товара представителю;
- возвраты;
- продажи;
- локальные корректировки;
- сдачу денежных средств.

Для строк товара передаются внутренний ID, артикул и `product_external_1c_id`. Для складов передаются их `external_1c_id`. До промышленного запуска все синхронизируемые товары и склады должны иметь идентификаторы 1С.

После создания документа в 1С вызывается `POST /confirm-export`:

```json
{
  "entity_type": "stock_document",
  "internal_id": "d0370217-c7b8-4e1d-87d6-52a4f3c998a4",
  "external_1c_id": "1c-doc-7812"
}
```

Для сдачи денег `entity_type` равен `cash_handover`. Повторное подтверждение тем же идентификатором безопасно; попытка заменить уже подтвержденный ID возвращает HTTP 409.

## Журнал обмена

Все входящие операции и подтверждения экспорта фиксируются в `integration_exchange_logs` со статусом, направлением, ключом операции, хэшем содержимого и текстом ошибки. Это позволяет видеть повторные попытки и расследовать расхождения.

## Рекомендуемая схема регламентного задания 1С

1. Выгрузить изменившиеся товары и склады, используя стабильный `operation_key` для каждой версии объекта.
2. Передать документы инвентаризации/начальных остатков при необходимости.
3. Получить `/outbox`.
4. Создать соответствующие документы 1С.
5. Для каждого успешно записанного объекта вызвать `/confirm-export`.
6. При сетевой ошибке безопасно повторить тот же запрос с тем же ключом.

## Владение данными

Рекомендуемый режим после запуска обмена:

- номенклатура и базовые цены — владелец 1С;
- оперативные продажи, выдачи, возвраты и сдача денег — владелец `ceh-sklad` до подтверждения экспорта;
- корректировки из 1С всегда создают отдельный документ и никогда не переписывают историю движений.
