# Интеграция с 1С

> Целевая конфигурация проекта уточнена: **1С:Управление нашей фирмой (УНФ) в облаке**. Этот документ описывает универсальный серверный контракт импорта/подтверждения. Сопоставление с документами УНФ, cloud bridge и staging-UAT описаны отдельно в [`INTEGRATION_UNF_CLOUD.md`](INTEGRATION_UNF_CLOUD.md).

## Общий принцип

Обмен двусторонний, идемпотентный и журналируемый. Облачная УНФ подключается через отдельный bridge; учетные данные tenant УНФ не передаются в Android/web и не хранятся в `ceh-sklad`. Bridge обращается к этому API только с отдельным сервисным ключом `X-1C-Key`; пользовательские JWT для обмена не используются.

## Настройка

В окружении backend задается отдельный секрет:

```env
INTEGRATION_1C_API_KEY=длинный-случайный-ключ
```

Все запросы bridge передают заголовок:

```http
X-1C-Key: длинный-случайный-ключ
```

Базовый адрес универсальных методов: `/api/v1/integration/1c`.

Для УНФ Cloud дополнительно доступны:

- `GET /api/v1/integration/1c/unf/profile` — версия и профиль контракта;
- `GET /api/v1/integration/1c/unf/outbox` — outbox с сопоставлением документов УНФ и диагностикой обязательных связей.

## Импорт справочников

### Номенклатура

`POST /products`

```json
{
  "operation_key": "product-42-version-7",
  "external_1c_id": "42",
  "sku": "A-001",
  "name": "Продукция А",
  "unit_name": "кг",
  "retail_price": "350.00",
  "wholesale_price": "310.00",
  "is_active": true
}
```

Если `external_1c_id` уже существует, справочник обновляется. Повтор запроса с тем же `operation_key` и тем же содержимым возвращает прежний результат и не создает дубль. Использование того же ключа с другим содержимым возвращает HTTP 409.

### Склады и виртуальные склады представителей

`POST /locations`

```json
{
  "operation_key": "location-main-version-2",
  "external_1c_id": "warehouse-main",
  "name": "Основной склад",
  "kind": "warehouse"
}
```

Для виртуального склада торгового представителя `kind` равен `representative`. Для целевого контура УНФ базовая стратегия — сопоставлять каждый такой объект с отдельным складом УНФ; альтернативная аналитика допускается только после UAT конкретной базы.

## Импорт остатков / инвентаризации

`POST /stock-adjustments`

```json
{
  "operation_key": "inventory-2026-09-03-main",
  "external_1c_id": "inventory-doc-10015",
  "location_external_1c_id": "warehouse-main",
  "comment": "Инвентаризация из 1С",
  "items": [
    {
      "product_external_1c_id": "42",
      "quantity_delta": "15.500"
    }
  ]
}
```

Это именно корректировка на дельту, а не прямое редактирование регистра. Документ и движения сохраняются в общей истории. Внешний идентификатор документа уникален, поэтому повторный импорт не создаст второе движение даже при использовании другого `operation_key`.

Абсолютный остаток из облачной УНФ нельзя автоматически записывать поверх текущего остатка `ceh-sklad`: между чтением облака и импортом могла пройти новая мобильная операция. Для сверки сначала вычисляется подтвержденное расхождение, после чего импортируется только дельта.

## Выгрузка из ceh-sklad в 1С

Универсальный `GET /outbox?limit=50` возвращает неподтвержденные документы:

- перемещения склад → склад;
- выдачи товара представителю;
- возвраты;
- продажи;
- локальные корректировки;
- сдачу денежных средств.

Для промышленного bridge УНФ рекомендуется использовать `/unf/outbox`: кроме исходных данных он сообщает требуемый документ УНФ, `ready_for_unf`, причины отсутствующих сопоставлений и `requires_split` для смешанной корректировки.

Для строк товара передаются внутренний ID, артикул и `product_external_1c_id`. Для складов передаются их `external_1c_id`. До промышленного запуска все синхронизируемые товары и склады должны иметь идентификаторы УНФ.

После создания документа в УНФ вызывается `POST /confirm-export`:

```json
{
  "entity_type": "stock_document",
  "internal_id": "d0370217-c7b8-4e1d-87d6-52a4f3c998a4",
  "external_1c_id": "1c-doc-7812"
}
```

Для сдачи денег `entity_type` равен `cash_handover`. Повторное подтверждение тем же идентификатором безопасно; попытка заменить уже подтвержденный ID возвращает HTTP 409.

Bridge считает операцию завершенной только после записи объекта в УНФ и успешного `/confirm-export`. Если связь оборвалась между этими стадиями, он обязан сначала найти уже созданный объект УНФ по собственному внешнему ключу и только затем повторить подтверждение — без создания второго документа.

## Журнал обмена

Все входящие операции и подтверждения экспорта фиксируются в `integration_exchange_logs` со статусом, направлением, ключом операции, хэшем содержимого и текстом ошибки. Это позволяет видеть повторные попытки и расследовать расхождения.

## Рекомендуемый цикл cloud bridge

1. Получить/передать изменившуюся номенклатуру, цены и склады с устойчивыми внешними ID.
2. Получить `/api/v1/integration/1c/unf/outbox`.
3. Пропустить объекты с `ready_for_unf=false` и зафиксировать их как требующие настройки сопоставлений.
4. Если `requires_split=true`, разделить корректировку на требуемые документы УНФ.
5. Записать/провести соответствующий документ в облачной УНФ через разрешенный конкретным tenant транспорт.
6. Сохранить устойчивый ID документа УНФ.
7. Вызвать `/api/v1/integration/1c/confirm-export`.
8. При сетевой ошибке повторить цикл идемпотентно, сначала проверив существование уже созданного документа УНФ.

## Владение данными

Рекомендуемый режим после запуска обмена:

- номенклатура и базовые цены — владелец УНФ;
- оперативные продажи, выдачи, возвраты и сдача денег — владелец `ceh-sklad` до подтверждения экспорта;
- корректировки из УНФ всегда создают отдельный документ и никогда не переписывают историю движений;
- конкретные реквизиты организации, кассы, покупателя и аналитики УНФ являются настройкой bridge для реального tenant, а не мобильного приложения.
