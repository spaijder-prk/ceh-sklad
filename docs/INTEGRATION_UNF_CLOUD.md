# Интеграция с 1С:УНФ в облаке

## Целевой контур

Целевая конфигурация — **1С:Управление нашей фирмой (УНФ)**, размещенная в облаке.

Архитектура специально не привязана к одному провайдеру облака:

1. если база работает в **1С:Фреш**, рекомендуется внешний bridge, который использует штатные механизмы интеграции Фреш с приложениями и наш HTTPS API;
2. если УНФ размещена у другого облачного провайдера и он публикует стандартный OData или отдельный HTTP-сервис, меняется только транспорт bridge;
3. складское ядро `ceh-sklad`, формат outbox и правила идемпотентности остаются одинаковыми.

Важно: API менеджера сервиса 1С:Фреш предназначен прежде всего для управления абонентами/приложениями сервиса. Бизнес-документы УНФ следует передавать через прикладной интеграционный транспорт/bridge, а не пытаться создавать через API управления облаком.

## Почему bridge, а не прямые вызовы из Android/web

Учетные данные облачной УНФ не должны попадать в Android-приложение, браузер или локальную очередь торгового представителя. Bridge работает как сервисный процесс и хранит учетные данные УНФ отдельно от пользовательских JWT.

Схема:

```text
Android / Web
      |
      v
ceh-sklad API + PostgreSQL
      |
      |  X-1C-Key, HTTPS
      v
UNF Cloud bridge
      |
      |  транспорт, разрешенный облачным провайдером
      v
1С:УНФ Cloud / 1С:Фреш
```

При использовании 1С:Фреш предпочтительно, чтобы инициатором обмена с прикладными данными был внешний bridge. Это не требует открывать PostgreSQL/FastAPI наружу помимо уже защищенного HTTPS API и позволяет централизовать retry, журналирование и сопоставление объектов.

## Контракт ceh-sklad для УНФ

Все методы защищены тем же отдельным `X-1C-Key`, что и универсальный контур 1С.

### Профиль интеграции

`GET /api/v1/integration/1c/unf/profile`

Возвращает версию контракта, целевую конфигурацию и базовое сопоставление документов. Bridge должен проверять `contract_version` при запуске.

### Обогащенный outbox

`GET /api/v1/integration/1c/unf/outbox?limit=50`

В отличие от универсального `/api/v1/integration/1c/outbox`, ответ дополнительно содержит:

- `unf_document` — рекомендуемый документ УНФ;
- `unf_operation` — смысл операции;
- `ready_for_unf` — все ли необходимые товары/склады сопоставлены с УНФ;
- `blocking_reasons` — почему объект пока нельзя отправить;
- `requires_split` — нужно ли разделить одну нашу операцию на несколько документов УНФ;
- `quantity_delta` для корректировок остатков.

После успешной записи документа в УНФ bridge вызывает уже существующий идемпотентный метод:

`POST /api/v1/integration/1c/confirm-export`

Документ исчезает из outbox только после этого подтверждения.

## Сопоставление документов УНФ

| Операция ceh-sklad | Документ УНФ | Правило |
| --- | --- | --- |
| `transfer` | Перемещение запасов | склад → склад |
| `issue_to_representative` | Перемещение запасов | центральный склад → склад торгового представителя |
| `representative_return` | Перемещение запасов | склад представителя → центральный склад |
| `sale` | Расходная накладная | продажа со склада представителя |
| положительная `adjustment` | Оприходование запасов | только положительные дельты |
| отрицательная `adjustment` | Списание запасов | только отрицательные дельты |
| смешанная `adjustment` | Оприходование + Списание | bridge обязан разделить на два документа |
| `cash_handover` | Поступление в кассу | прием наличной выручки представителя |

### Склады торговых представителей

Базовая стратегия проекта: **каждый торговый представитель имеет отдельный склад в УНФ**. Его `external_1c_id` хранится у виртуального склада `ceh-sklad`.

Это позволяет однозначно отражать:

- выдачу товара представителю;
- возврат товара;
- продажу именно с остатка представителя;
- сверку фактического остатка представителя между системами.

Если в конкретной базе УНФ принято учитывать представителей другой аналитикой, это меняется в bridge после UAT, а не в складском ядре.

## Продажи

По умолчанию одна подтвержденная продажа `ceh-sklad` соответствует одной **Расходной накладной** УНФ. Количество и цена берутся из уже проведенного документа `ceh-sklad`, поэтому изменение текущей цены номенклатуры в УНФ не должно менять историческую сумму продажи.

До промышленного запуска нужно выбрать правило покупателя:

- для оптовой/идентифицированной продажи — реальный контрагент УНФ;
- для анонимной розницы — согласованный служебный контрагент либо отдельный сценарий агрегации розничных продаж.

Текущий контракт сохраняет каждую мобильную продажу отдельно. Автоматическое объединение нескольких продаж в один документ УНФ без отдельного правила не выполняется.

## Сдача денег

`cash_handover` отображается в **Поступление в кассу**. На стороне bridge/УНФ необходимо один раз зафиксировать:

- кассу-получателя;
- аналитику плательщика/подотчетного лица;
- статью движения денежных средств;
- организацию, если в УНФ ведется несколько организаций.

Эти реквизиты являются настройкой конкретной базы УНФ и не должны быть захардкожены в мобильном приложении.

## Импорт из УНФ в ceh-sklad

Универсальные входящие методы остаются без изменений:

- `POST /api/v1/integration/1c/products` — номенклатура и две цены;
- `POST /api/v1/integration/1c/locations` — склады и склады представителей;
- `POST /api/v1/integration/1c/stock-adjustments` — подтвержденные корректировки/начальные остатки дельтой.

Номенклатура и базовые цены после запуска считаются данными УНФ. Bridge передает стабильный `external_1c_id` и стабильный `operation_key` для версии объекта.

### Остатки

Автоматически «перезаписывать» текущий остаток абсолютным значением из УНФ нельзя: между чтением УНФ и записью мог пройти новый мобильный документ. Поэтому текущий API принимает только **дельту** и создает отдельный документ движения.

Абсолютная сверка остатков выполняется как приемочная/инвентаризационная процедура: определяется расхождение, затем в `ceh-sklad` передается только подтвержденная дельта.

## Идемпотентность

Bridge обязан считать операцию завершенной только после двух стадий:

1. документ успешно записан/проведен в УНФ и получен его устойчивый идентификатор;
2. `ceh-sklad` успешно принял `/confirm-export` с этим идентификатором.

Если сеть оборвалась между стадиями, bridge повторно ищет документ УНФ по собственному внешнему ключу и повторяет подтверждение. Создавать второй документ без такой проверки запрещено.

## Особенности 1С:Фреш

Для 1С:Фреш проект исходит из следующих принципов:

- УНФ является приложением облачного сервиса, а не локальной файловой базой;
- взаимодействие выполняется через опубликованные сервисом механизмы удаленного доступа/интеграции;
- для прикладного обмена используется сервисный пользователь с минимальными правами удаленного доступа;
- конкретный URL и допустимый транспорт определяются фактической публикацией приложения и правами абонента;
- стандартный OData не считается гарантированно доступным «по умолчанию» и должен быть подтвержден на реальном tenant;
- если OData недоступен, bridge использует штатный механизм передачи/интеграции объектов Фреш либо согласованное расширение УНФ.

## Что нужно получить для подключения реального облака

Для UAT потребуются не секреты в репозитории, а параметры конкретного экземпляра:

- точный облачный провайдер (1С:Фреш или другой);
- URL приложения УНФ;
- версия УНФ;
- сервисный пользователь/способ авторизации;
- доступный транспорт: интеграция Фреш, HTTP-сервис, OData или утвержденное расширение;
- организация УНФ;
- касса для приема выручки;
- правило покупателя для розничных продаж;
- список складов и правило создания складов торговых представителей.

До получения этих параметров нельзя корректно зафиксировать имена метаданных/OData entity sets и реквизиты документов конкретной базы.

## Приемочные сценарии УНФ Cloud

1. Импортировать одну номенклатуру и обе цены из УНФ.
2. Сопоставить центральный склад и склад тестового представителя.
3. Выдать товар представителю и получить в УНФ `Перемещение запасов`.
4. Провести розничную и оптовую продажу и проверить `Расходную накладную` с исторической ценой.
5. Вернуть товар и проверить обратное `Перемещение запасов`.
6. Сдать деньги и проверить `Поступление в кассу`.
7. Создать смешанную корректировку и убедиться, что bridge формирует два документа.
8. Повторить доставку каждого сообщения и убедиться в отсутствии дублей.
9. Оборвать связь после записи документа УНФ, но до `/confirm-export`, затем проверить безопасное восстановление.
10. Сверить остатки центрального склада и представителя после полного цикла.
