# Приемка staging

Ручной workflow `Staging-приемка` предназначен для проверки уже развернутого HTTPS staging-окружения. По умолчанию он не создает складских или денежных документов.

Целевой контур 1С — **1С:Управление нашей фирмой в облаке**. Подробная схема bridge и сопоставления документов приведена в `docs/INTEGRATION_UNF_CLOUD.md`.

## GitHub Secrets

В Actions необходимо задать:

- `CEH_STAGING_REP_LOGIN` — логин отдельного тестового торгового представителя;
- `CEH_STAGING_REP_PASSWORD` — его пароль;
- `CEH_STAGING_1C_KEY` — сервисный ключ тестового контура `ceh-sklad` ↔ bridge УНФ; необязателен для остальных проверок.

Учетные данные самой облачной УНФ не должны попадать в эти переменные, Android или web. Их хранит и использует отдельный bridge/секретное хранилище интеграционного контура.

Не используйте production-пароли для staging-приемки.

## Входные параметры workflow

- `base_url` — HTTPS origin staging;
- `location_id` — виртуальный склад тестового представителя;
- `product_id` — товар с известным достаточным остатком;
- `requests`, `concurrency`, `quantity` — параметры load-test;
- `require_unf_ready=false` — по умолчанию показывает проблемы сопоставления УНФ как диагностику, но не останавливает smoke;
- `execute_sales=false` — безопасное значение по умолчанию.

Перед промышленным UAT УНФ рекомендуется повторить workflow с `require_unf_ready=true`. Тогда любой документ outbox, у которого отсутствует обязательный `external_1c_id` товара/склада, завершит приемку ошибкой.

## Что проверяется без изменения данных

1. `GET /health/ready`: доступ к PostgreSQL и Alembic revision;
2. вход тестового представителя и соответствие его виртуального склада;
3. чтение собственного остатка, долга и истории;
4. WSS handshake `/api/v1/realtime`;
5. при наличии `CEH_STAGING_1C_KEY` — профиль `/api/v1/integration/1c/unf/profile` с целью `1С:Управление нашей фирмой` и `deployment=cloud`;
6. read-only `/api/v1/integration/1c/unf/outbox`: количество готовых объектов и список блокирующих сопоставлений;
7. dry-run `scripts/load_test.py`, включая проверку достаточности остатка.

## Строгая готовность УНФ

В строгом режиме `require_unf_ready=true` проверяется, что все попавшие в выборку outbox документы имеют обязательные связи с УНФ:

- номенклатура имеет `external_1c_id`;
- склад-источник/получатель сопоставлен;
- склад торгового представителя сопоставлен;
- место инвентаризационной корректировки сопоставлено.

Смешанная корректировка не считается ошибкой сама по себе: она помечается `requires_split=true`, и bridge должен создать в УНФ отдельные документы `Оприходование запасов` и `Списание запасов`.

## Реальные тестовые продажи

Только при ручном выборе `execute_sales=true` workflow запускает load-test с защитной переменной `CEH_LOAD_TEST_CONFIRM`. Каждая продажа получает уникальный `operation_key`, а повтор первой операции проверяет идемпотентность.

После такого прогона тестовые продажи нужно учитывать как реальные документы staging и при необходимости закрыть их корректирующими документами, а не редактировать историю напрямую.

## UAT с облачной УНФ

После успешного read-only smoke необходимо проверить на реальной тестовой базе УНФ:

1. выдача представителю → `Перемещение запасов`;
2. продажа → `Расходная накладная`;
3. возврат → обратное `Перемещение запасов`;
4. сдача денег → `Поступление в кассу`;
5. смешанная корректировка → отдельные документы оприходования и списания;
6. повторная доставка не создает дубль;
7. разрыв связи после записи документа УНФ, но до `/confirm-export`, восстанавливается без второго документа;
8. остатки центрального склада и склада представителя совпадают после полного цикла.

Если облачный провайдер — 1С:Фреш, transport bridge должен быть подтвержден на фактическом tenant. Наличие стандартного OData нельзя считать гарантированным до этой проверки.

## Что сохранить в релизном журнале

- облачный провайдер УНФ и URL тестового приложения;
- версия УНФ;
- доступный транспорт bridge;
- URL staging и дата прогона;
- номер GitHub Actions run;
- Alembic revision;
- количество запросов и concurrency;
- success/error count, throughput, p50/p95/max;
- результат WSS и строгой проверки сопоставлений УНФ;
- созданные ID тестовых документов УНФ;
- идентификатор подписанного Android artifact после отдельного release workflow;
- результат приемки в тестовой базе УНФ.
