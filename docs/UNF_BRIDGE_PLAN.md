# План промышленного bridge для облачной 1С:УНФ

## Назначение

`ceh-sklad` предоставляет транспорт-независимый контракт УНФ Cloud:

- `/api/v1/integration/1c/unf/profile`;
- `/api/v1/integration/1c/unf/outbox`;
- универсальные входящие методы;
- `/api/v1/integration/1c/confirm-export` для одного внешнего документа;
- `/api/v1/integration/1c/confirm-export-batch` для одной операции, которая стала несколькими документами УНФ.

В репозитории уже есть пакет `unf-bridge/`: HTTPS-клиент `ceh-sklad`, модели `unf-cloud-v2`, планировщик и безопасный dry-run CLI. Реальный transport adapter конкретного tenant будет добавлен после получения параметров облака.

Bridge не входит в Android/web и не использует пользовательские JWT.

## Почему transport нельзя захардкодить заранее

Фраза «УНФ в облаке» не определяет один технический endpoint. Возможны:

- 1С:Фреш с разрешенными для tenant механизмами удаленной интеграции/передачи данных;
- иной облачный хостинг УНФ с опубликованным HTTP-сервисом;
- иной облачный хостинг с опубликованным стандартным OData;
- согласованное расширение УНФ с собственным HTTP API.

Поэтому слой бизнес-сопоставления отделен от transport adapter.

## Текущая структура bridge

```text
unf-bridge/
  unf_bridge/
    models.py             # контракт unf-cloud-v2
    ceh_client.py         # profile/outbox/confirm
    planner.py            # устойчивые ключи и split-план
    cli.py                # read-only dry-run
  tests/
    test_planner.py
```

Следующий слой после получения tenant:

```text
unf_bridge/
  transport/
    fresh.py              # если tenant — 1С:Фреш
    odata.py              # если опубликован OData
    http_service.py       # если согласован HTTP-сервис/расширение
  worker.py
  retry_store.py
  health.py
```

Transport adapter должен иметь одинаковый внутренний интерфейс:

- проверить доступ и версию приложения;
- найти объект по устойчивому внешнему ключу;
- создать/обновить разрешенный объект;
- создать и при необходимости провести документ УНФ;
- вернуть устойчивый ID/ссылку документа;
- различать retryable и permanent ошибки.

## Обязательные настройки tenant

До финального transport adapter нужны:

1. провайдер/площадка;
2. URL приложения УНФ;
3. версия УНФ;
4. разрешенный способ удаленной авторизации;
5. разрешенный transport;
6. организация;
7. основной склад и правило складов торговых представителей;
8. касса приема выручки;
9. статья движения денег;
10. правило контрагента для анонимной розничной продажи;
11. правило проведения документов — записывать или сразу проводить;
12. часовой пояс базы.

См. `UNF_TENANT_CHECKLIST.md`. Эти параметры нельзя заменять догадками в коде.

## Устойчивые внешние ключи

Планировщик bridge формирует ключ:

```text
ceh-sklad:<entity_type>:<internal_id>
```

Для mixed adjustment используются два дочерних ключа:

```text
ceh-sklad:stock_document:<internal_id>:receipt
ceh-sklad:stock_document:<internal_id>:writeoff
```

Перед любой повторной попыткой создания transport adapter сначала ищет документ УНФ по этому ключу. Это основной барьер от дубля при неопределенном результате HTTP-запроса.

## Идемпотентный алгоритм outbound

Для каждого элемента `/unf/outbox`:

1. если `ready_for_unf=false`, не создавать документ и вывести `blocking_reasons`;
2. построить план и устойчивые ключи;
3. для каждого планового документа найти существующий объект УНФ по ключу;
4. создать только отсутствующие документы;
5. сохранить устойчивые ID результатов;
6. для обычной операции вызвать `/confirm-export`;
7. для `requires_split=true` вызвать `/confirm-export-batch` со всеми созданными документами и их `external_kind`;
8. только после успешного confirm считать элемент завершенным.

`confirm-export-batch` хранит отдельные строки `integration_export_links`, поэтому одна mixed adjustment может быть связана одновременно с `Оприходование запасов` и `Списание запасов`. Повтор того же набора безопасен; другой набор возвращает конфликт.

При любой сетевой неопределенности шаг создания не повторяется до поиска по устойчивому ключу.

## Inbound из УНФ

Номенклатура/цены/склады передаются в универсальные endpoints `ceh-sklad` со стабильными `external_1c_id`, `operation_key` и повтором того же сообщения при временной ошибке.

Для остатков bridge не передает абсолютное число как «истину». После сверки он вычисляет подтвержденную дельту и создает `/stock-adjustments`.

## Dry-run

После установки пакета:

```bash
pip install -e './unf-bridge[dev]'
CEH_API_URL=https://staging.example.ru \
CEH_1C_KEY='***' \
ceh-unf-bridge --limit 50
```

Команда проверяет `unf-cloud-v2`, читает outbox, показывает blocked mappings и план документов/устойчивых ключей. Она **не пишет в УНФ и не вызывает confirm**.

HTTP разрешается только явным `--allow-http` для локальной разработки.

## Наблюдаемость

Будущий рабочий bridge должен экспортировать:

- время последнего успешного цикла;
- размер outbound очереди;
- permanent/retryable ошибки;
- возраст старейшего элемента;
- последние ID документов УНФ;
- версию transport adapter;
- health tenant без раскрытия credentials.

На стороне `ceh-sklad` доступны `/api/v1/system/status`, `unf_mapping_ready` и счетчики несопоставленных справочников.

## Критерий завершения bridge

Bridge готов только после UAT полного цикла: выдача → продажа → возврат → сдача денег → смешанная корректировка → повторная доставка → искусственный разрыв связи → сверка остатков без дублей.
