# План промышленного bridge для облачной 1С:УНФ

## Назначение

`ceh-sklad` уже предоставляет транспорт-независимый контракт УНФ Cloud: `/api/v1/integration/1c/unf/profile`, `/api/v1/integration/1c/unf/outbox`, универсальные входящие методы и `/confirm-export`.

Bridge — отдельный сервисный процесс между этим контрактом и конкретным экземпляром облачной УНФ. Он не входит в Android/web и не должен использовать пользовательские JWT.

## Почему transport нельзя захардкодить заранее

Фраза «УНФ в облаке» не определяет один технический endpoint. Возможны как минимум:

- 1С:Фреш с разрешенными для tenant механизмами удаленной интеграции/передачи данных;
- иной облачный хостинг УНФ с опубликованным HTTP-сервисом;
- иной облачный хостинг с опубликованным стандартным OData;
- согласованное расширение УНФ с собственным HTTP API.

Поэтому слой бизнес-сопоставления отделен от transport adapter.

## Структура будущего bridge

```text
bridge/
  config                 # URL tenant, секреты, организация, касса, покупатель
  ceh_client              # /unf/outbox, generic imports, /confirm-export
  transport/
    fresh                 # если реальный tenant — 1С:Фреш
    odata                 # если провайдер публикует OData
    http_service          # если есть согласованный HTTP-сервис УНФ
  mapping/
    products
    warehouses
    documents
    cash
  worker
  retry_store
  health
```

Transport adapter должен иметь одинаковый внутренний интерфейс:

- проверить доступ/версию приложения;
- найти объект по устойчивому внешнему ключу;
- создать/обновить номенклатуру или склад при разрешенном направлении обмена;
- создать и при необходимости провести документ УНФ;
- вернуть устойчивый ID/ссылку документа;
- различать retryable и permanent ошибки.

## Обязательные настройки tenant

До написания финального transport adapter необходимо получить от реальной облачной базы:

1. провайдер/площадка;
2. URL приложения УНФ;
3. версию УНФ;
4. разрешенный способ удаленной авторизации;
5. разрешенный transport;
6. организацию;
7. основной склад и правило складов торговых представителей;
8. кассу приема выручки;
9. статью движения денег;
10. правило контрагента для анонимной розничной продажи;
11. правило проведения документов — записывать или сразу проводить;
12. часовой пояс базы.

Эти параметры нельзя подменять догадками в исходном коде.

## Идемпотентный алгоритм outbound

Для каждого элемента `/unf/outbox`:

1. если `ready_for_unf=false`, не создавать документ и вывести `blocking_reasons`;
2. сформировать устойчивый ключ bridge из `entity_type + internal_id`;
3. найти документ УНФ по этому ключу;
4. если документа нет — создать его;
5. если `requires_split=true`, создать согласованный набор дочерних документов и сохранить их связь с одним internal ID;
6. получить устойчивый ID результата;
7. вызвать `/api/v1/integration/1c/confirm-export`;
8. только после успешного подтверждения считать элемент завершенным.

При любой сетевой неопределенности шаг создания не повторяется до повторного поиска по устойчивому ключу.

## Inbound из УНФ

Номенклатура/цены/склады передаются в универсальные endpoints `ceh-sklad` с:

- стабильным `external_1c_id`;
- стабильным `operation_key` на версию сообщения;
- повтором того же сообщения при временной ошибке.

Для остатков bridge не передает абсолютное число как «истину». После сверки он вычисляет подтвержденную дельту и создает `/stock-adjustments`.

## Наблюдаемость

Bridge должен экспортировать минимум:

- время последнего успешного цикла;
- размер outbound очереди;
- число permanent/retryable ошибок;
- возраст старейшего элемента;
- последние ID документов УНФ;
- текущую версию transport adapter;
- health подключения к tenant без раскрытия логина/пароля.

На стороне `ceh-sklad` уже доступны `/api/v1/system/status` и диагностика `unf_mapping_ready`.

## Критерий завершения bridge

Bridge считается готовым не после первого HTTP 200, а после UAT полного цикла: выдача → продажа → возврат → сдача денег → корректировка → повторная доставка → искусственный разрыв связи → сверка остатков без дублей.
