# Политика DeletionMark номенклатуры УНФ

Bridge не должен угадывать, что делать с пометкой удаления товара в конкретной базе УНФ. Поведение задается несекретным `product_deletion_policy` в tenant mapping.

Поддерживаются режимы:

- `ignore` — backward-compatible режим: `DeletionMark` не участвует в импорте;
- `skip` — помеченный товар пропускается без изменения `ceh-sklad`;
- `block` — помеченный товар делает импорт blocked до ручного решения;
- `archive_if_zero_stock` — bridge выполняет read-only precheck и затем использует отдельный идемпотентный archive endpoint.

Для `skip`, `block` и `archive_if_zero_stock` нужно задать `product_fields.deletion_mark` из фактического `$metadata`. Для `archive_if_zero_stock` дополнительно обязательно поле версии `product_fields.version` (например, если оно опубликовано как `DataVersion`). Версия и состояние `DeletionMark` входят в client operation key, поэтому цикл «активен → удален → восстановлен → удален снова» не переиспользует старую идемпотентную операцию.

## Атомарная гарантия `archive_if_zero_stock`

Read-only `/products/{external_1c_id}/archive-check` нужен для понятного dry-run и раннего blocked-результата, но не является единственной защитой.

Фактическая запись выполняется через `/products/{external_1c_id}/archive`:

1. operation key сериализуется по записи журнала интеграции;
2. строка `Product` блокируется `FOR UPDATE`;
3. сервер повторно считает суммарный остаток;
4. только при нулевом остатке устанавливается `is_active=false` и операция фиксируется как completed.

Все stock-changing сервисы (`transfer`, `adjustment`, `sale`, включая выдачу/возврат через transfer) сначала берут тот же Product row lock и проверяют `is_active`, а уже затем блокируют строки остатков. Поэтому возможны только два корректных исхода гонки:

- складское движение получило lock первым → архивирование дождется его commit и увидит новый ненулевой остаток;
- архивирование получило lock первым → движение дождется commit и получит `409`, потому что товар уже архивирован.

Повтор completed archive operation key после последующей реактивации товара возвращает `repeated=true` и **не архивирует товар заново**. Это защищает от позднего сетевого retry старой версии операции.

До UAT рекомендуется `block`. После проверки поведения вашей УНФ можно осознанно выбрать `skip` или `archive_if_zero_stock`. `ignore` оставлен только для обратной совместимости и должен быть явно принят в release record, если используется в production.
