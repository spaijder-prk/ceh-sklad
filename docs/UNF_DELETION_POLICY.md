# Политика DeletionMark номенклатуры УНФ

Bridge не должен угадывать, что делать с пометкой удаления товара в конкретной базе УНФ. Поведение задается несекретным `product_deletion_policy` в tenant mapping.

Поддерживаются режимы:

- `ignore` — backward-compatible режим: `DeletionMark` не участвует в импорте;
- `skip` — помеченный товар пропускается без изменения `ceh-sklad`;
- `block` — помеченный товар делает импорт blocked до ручного решения;
- `archive_if_zero_stock` — bridge выполняет read-only precheck остатка и архивирует товар только если он уже существует, активен и суммарный остаток равен нулю.

Для `skip`, `block` и `archive_if_zero_stock` нужно задать `product_fields.deletion_mark` из фактического `$metadata`. Для `archive_if_zero_stock` дополнительно обязательно поле версии `product_fields.version` (например, если оно опубликовано как `DataVersion`). Версия и состояние `DeletionMark` входят в client operation key, поэтому цикл «активен → удален → восстановлен → удален снова» не переиспользует старую идемпотентную операцию.

`archive_if_zero_stock` не ослабляет backend-инвариант: даже после успешного precheck сервер повторно проверяет фактический остаток в транзакции импорта и возвращает `409`, если он успел измениться.

До UAT рекомендуется `block`. После проверки поведения вашей УНФ можно осознанно выбрать `skip` или `archive_if_zero_stock`. `ignore` оставлен только для обратной совместимости и должен быть явно принят в release record, если используется в production.
