## Почему виды цен задаются явно

В УНФ розничная и оптовая цены являются настраиваемыми **видами цен**. Названия, формулы и состав видов цен определяются в самой базе. Поэтому bridge не предполагает наличие фиксированных полей `retail`/`wholesale`: в mapping указываются два фактических `Ref_Key`, которые являются источником `retail_price` и `wholesale_price` для `ceh-sklad`.

## Если это 1С:Фреш

Для приложений на `1cfresh.com` стандартный OData публикуется по адресу:

`<URL приложения>/odata/standard.odata/`

Первую проверку выполняйте только read-only probe из `unf-bridge`:

```bash
export UNF_FRESH_URL='https://1cfresh.com/a/.../...'
export UNF_FRESH_LOGIN='service-user'
export UNF_FRESH_PASSWORD='***'
ceh-unf-fresh-probe
```

После первичного discovery заполните `unf-bridge/unf-tenant.example.json`, сохраните отдельной несекретной конфигурацией и повторите:

```bash
ceh-unf-fresh-probe --mapping /path/to/unf-tenant.json
```

Команда сверит EntitySet и поля устойчивых ключей с реальным `$metadata` до любой записи. Сервисные credentials в вывод не включаются.

Нужно определить фактические EntitySet/реквизиты для:

- номенклатуры;
- видов цен и актуальных цен номенклатуры;
- складов;
- организации;
- контрагентов;
- перемещения запасов;
- расходной накладной;
- поступления в кассу;
- оприходования и списания запасов;
- кассы;
- статьи ДДС;
- плательщика/подотчетного лица, используемого при сдаче выручки.

До получения metadata конкретного tenant эти имена в production-конфигурацию не зашиваются.

## Read-only проверки произвольных справочников

Bridge `0.8.1` поддерживает `reference_checks` в tenant mapping. Это позволяет после получения реального `$metadata` проверять существование кассы, статьи ДДС, плательщика и других tenant-specific объектов **без изменения Python-кода**.

Пример:

```json
{
  "reference_checks": [
    {
      "name": "cashbox",
      "resource": "Catalog_ФактическийEntitySetКасс",
      "ref_key": "11111111-1111-1111-1111-111111111111"
    },
    {
      "name": "cash_flow_item",
      "resource": "Catalog_ФактическийEntitySetСтатейДДС",
      "ref_key": "22222222-2222-2222-2222-222222222222"
    }
  ]
}
```

Правила:

- `name` — уникальное безопасное имя проверки;
- `resource` — точный EntitySet из фактического `$metadata`, без догадок;
- `ref_key` — реальный GUID `Ref_Key` объекта;
- `ceh-unf-fresh-health` сначала убеждается, что `resource` опубликован в `$metadata`, затем выполняет только read-only поиск по GUID;
- отсутствующий EntitySet блокирует metadata validation;
- отсутствующий объект переводит health в `degraded` и попадает в `reference_validation_errors`;
- пароли, токены и другие секреты в `reference_checks` не хранятся.

Для нескольких плательщиков можно добавить отдельную проверку на каждый реально используемый `Ref_Key`. Это не заменяет `representative_payer_refs`: первый механизм проверяет существование внешнего объекта, второй определяет бизнес-сопоставление представителя с плательщиком.
