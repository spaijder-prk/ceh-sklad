# Резервное копирование PostgreSQL

Для production предусмотрены два эксплуатационных скрипта:

- `ops/backup-postgres.sh` — создать и проверить резервную копию;
- `ops/restore-postgres.sh` — восстановить базу из проверенного архива.

Оба скрипта по умолчанию используют `compose.production.yml` и `.env.production`. Параметры можно переопределить переменными `CEH_COMPOSE_FILE` и `CEH_ENV_FILE`.

## Создание резервной копии

```bash
ops/backup-postgres.sh
```

По умолчанию архивы сохраняются в `./backups/`, который исключен из Git. Формат — PostgreSQL custom archive (`pg_dump --format=custom`). После создания скрипт:

1. проверяет, что архив не пуст;
2. читает его каталог через `pg_restore --list`;
3. только после успешной проверки переименовывает временный файл в итоговый `.dump`;
4. создает соседний `.sha256`;
5. удаляет архивы старше установленного срока хранения.

Параметры:

```text
CEH_BACKUP_DIR=/srv/ceh-backups
CEH_BACKUP_RETENTION_DAYS=14
```

`CEH_BACKUP_RETENTION_DAYS=0` отключает автоматическое удаление. Рекомендуется хранить production-копии не только на том же сервере: после локального создания передавайте архив и `.sha256` в отдельное защищенное хранилище.

Сам PostgreSQL custom archive не шифруется скриптом. Если резервная копия содержит чувствительные данные, внешнее хранилище или дополнительный слой архивации должны обеспечивать шифрование на диске и при передаче.

## Планировщик

Пример ежедневного запуска через cron в 02:30:

```cron
30 2 * * * cd /srv/ceh-sklad && CEH_BACKUP_DIR=/srv/backups/ceh ./ops/backup-postgres.sh >> /var/log/ceh-backup.log 2>&1
```

Следите, чтобы пользователь cron имел доступ к Docker и каталогу резервных копий. Для systemd timer используйте те же команды и переменные окружения.

## Восстановление

Восстановление является разрушительной операцией: текущая целевая база удаляется и создается заново. Поэтому одного имени файла недостаточно — требуется явное подтверждение:

```bash
CEH_CONFIRM_RESTORE=YES ops/restore-postgres.sh /srv/backups/ceh/ceh_sklad_20260905T020000Z.dump
```

Перед удалением текущей базы скрипт:

1. проверяет SHA-256, если рядом есть `<архив>.sha256`;
2. проверяет структуру архива через `pg_restore --list`;
3. запускает PostgreSQL/Redis;
4. останавливает backend и web;
5. завершает оставшиеся подключения к целевой БД;
6. удаляет и заново создает только разрешенное имя рабочей БД;
7. выполняет `pg_restore --exit-on-error`;
8. после успешного восстановления запускает backend и web.

Если restore завершается ошибкой после остановки приложения, backend и web намеренно остаются остановленными: это защищает пользователей от работы с частично восстановленной БД.

При последующем запуске backend его production entrypoint выполняет `alembic upgrade head`, поэтому копия от более старой версии приложения будет доведена до текущей схемы миграциями.

## Контроль после восстановления

Обязательно проверьте:

```bash
docker compose --env-file .env.production -f compose.production.yml ps
curl https://<ваш-домен>/health
```

Затем в панели сверяйте минимум:

- количество складов и товаров;
- несколько контрольных складских остатков;
- остаток выбранного торгового представителя;
- его задолженность;
- последние товарные документы и денежные операции;
- наличие актуальной Alembic-версии.

В production полезно регулярно выполнять тестовое восстановление на отдельном сервере/в отдельной БД. Наличие файлов `.dump` без проверенной процедуры восстановления не является полноценной стратегией резервного копирования.
