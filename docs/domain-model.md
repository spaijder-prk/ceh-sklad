# Предметная модель складского учета

## Два слоя учета

Система хранит товар в двух взаимосвязанных представлениях.

Первый слой — неизменяемый журнал проводок `stock_postings`. Он отвечает за историю: какая операция, когда и куда переместила товар.

Второй слой — регистр текущих остатков:

- `warehouse_stock_balances` — остатки по складам;
- `representative_stock_balances` — остатки у торговых представителей.

Регистр текущих остатков обновляется в той же транзакции, что и документ с проводками. Поэтому журнал и текущий остаток не расходятся при штатной работе.

## Защита от конкурентного списания

Перед списанием сервис получает строку текущего остатка с блокировкой `SELECT ... FOR UPDATE`. До завершения транзакции другой запрос не может изменить ту же строку.

Это защищает от ситуации, когда два параллельных запроса одновременно видят, например, 10 единиц товара и оба пытаются списать по 8.

На уровне БД дополнительно действует ограничение `quantity >= 0`.

## Владельцы товара

Товар может находиться:

- на складе;
- у торгового представителя.

Одна историческая товарная проводка относится ровно к одному владельцу: либо к складу, либо к торговому представителю.

## Документы

Поддерживаются следующие типы документов:

- `receipt` — приход товара на склад;
- `issue_to_representative` — выдача товара со склада торговому представителю;
- `representative_return` — возврат товара от представителя на склад;
- `warehouse_transfer` — перемещение между складами;
- `sale` — продажа товара торговым представителем;
- `adjustment` — резерв для будущих корректировок.

## Продажа

При продаже:

1. блокируется и уменьшается текущий остаток представителя;
2. создается отрицательная товарная проводка;
3. цена фиксируется в проводке на момент продажи;
4. цена выбирается из розничной или оптовой цены товара;
5. в денежном регистре создается положительная проводка на сумму продажи — задолженность представителя перед компанией увеличивается.

Изменение цены товара в будущем не меняет сумму уже зарегистрированной продажи.

## Сдача денег

Сдача денег создает отрицательную денежную проводку. Итоговая задолженность представителя определяется суммой всех денежных проводок.

Сдачу денег регистрирует администратор. Торговый представитель не может самостоятельно уменьшить собственную задолженность.

## Идемпотентность и интеграция с 1С

Для документов и денежных операций предусмотрено поле `external_id`. При повторной отправке операции с тем же `external_id` API возвращает уже созданную операцию вместо повторного списания.

Это является базовым механизмом безопасного обмена с 1С при повторной доставке сообщений.

## Обновления в реальном времени

WebSocket `/api/v1/ws/updates` отправляет уведомления после успешно завершенной транзакции.

Событие не содержит полный снимок остатков. Клиент получает признак изменения и перечитывает нужный REST-ресурс. Такой подход не дублирует бизнес-логику фильтрации ролей в WebSocket-слое.

Текущая реализация хранит WebSocket-соединения в памяти одного процесса. Для горизонтального масштабирования backend потребуется общий канал публикации, например Redis Pub/Sub.

## Миграции

`0001_initial` создает основной журнал учета, пользователей и справочники.

`0002_current_balances` создает регистр текущих остатков и автоматически заполняет его агрегатами существующих проведенных документов.

Если исторический журнал уже содержит отрицательный итоговый остаток, миграция регистра должна завершиться ошибкой вместо молчаливого переноса некорректных данных.

## Следующие предметные задачи

- сторнирование документов обратными проводками;
- журнал документов для администратора и руководителя;
- отчеты по продажам, задолженности и движениям;
- двусторонняя синхронизация с 1С;
- Redis-канал для WebSocket при нескольких экземплярах backend.
